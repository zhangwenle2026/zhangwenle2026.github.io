## 🚨 数据解析必读：千分位逗号陷阱（2026-04-23 修复）

**kdata JSON 返回的所有数值字段均为带千分位逗号的字符串，直接转 int/float 将得到 0 或报错！**

- rows 结构为 **dict 列表**，取值：`r.get('fin_ord_num', '0')`（不是 `r[1]`）
- 所有量类字段（订单量、UV、取消量等）解析前必须：`int(str(r.get('field', '0')).replace(',', ''))`
- 率/占比类字段（如 `"12.34%"`）：`float(str(r.get('field', '0')).replace('%','').replace(',',''))`
- ✅ 正确：`int(str(r.get('fin_ord_num', '0')).replace(',', ''))`
- ❌ 错误：`int(r['fin_ord_num'])` 或 `int(r.get('fin_ord_num', 0))`

## 🚨 大盘总量必须剔除 brand_id=0（2026-06-11 强制规则）

> **每次报告大盘数据前，必须完成以下两步，直接用聚合查询的 raw_total 是错的。**

**正确两步法（不得跳过）：**

```
步骤 1：聚合查询得 raw_total（无 --filter，不带 --group-by）
步骤 2：从分组查询结果中找 brand_id=0 的行，取其 fin_ord_num 值为 unattributed
         （若分组查询中无 brand_id=0 行，则 unattributed = 0）
步骤 3：grand_total = raw_total - unattributed
```

- 大盘 WoW = (grand_curr - grand_prev) / grand_prev × 100
- 品牌大盘贡献 = (品牌当期量 - 品牌对比期量) / grand_curr × 100
- ❌ 禁止直接用 raw_total 作为大盘；❌ 禁止忘记查对比期的 brand_id=0 值

> ❌ 历史错误（2026-06-11）：直接用 449,389（raw_total）作为大盘，实际 brand_id=0 占 66,980，真实大盘应为 382,409。

## 🚨 输出前必须执行的强制检查：当期 vs 对比期不得写反

**每次输出任何数据前，必须逐条确认以下三点，缺一不可：**

1. **变量绑定**：当期数据 = 用户指定的"分析日期"对应的查询结果（curr）；对比期数据 = 用户指定的"对比日期"对应的查询结果（prev）。**禁止凭肉眼排列数字，必须从变量取值。**

2. **同一品牌的当期/对比期查询必须串行**：同一品牌的当期和对比期不得并行查询后依赖文件名区分，必须串行执行，每次查询在输出中明确打印日期范围（如 `=== 04-01~04-22（当期）===`），再读取结果赋值给 curr/prev 变量。不同品牌之间可以并行分析（spawn sub-agent），但同一品牌的两期数据必须串行。

3. **方向自检**：输出前对每一个指标做验算——
   - curr > prev → PoP 必须为正（+）
   - curr < prev → PoP 必须为负（-）
   - 如果符号和方向不一致，**停止输出，重新检查**

4. **多品牌汇总前**：主 agent 汇总 sub-agent 结果时，再过一遍每个品牌的 curr/prev 方向，确认无误后再输出

> ❌ 历史错误案例（2026-04-23）：Balbun 分析中，满折覆盖率、Feeds CTR 等多个指标当期/对比期列写反，导致结论方向完全错误。根因：手工排列数字时顺序搞反。**此后所有数据必须从变量直接取值，禁止手工填写。**

## 🚨 报告输出规范：只陈述事实，不给无依据的推断

**报告中只能陈述数据事实，禁止在没有直接证据支撑的情况下断定因果关系。**

### 规则

1. **只写事实**：指标数值、PoP 变化、是否触发阈值——这些是事实，可以写。
2. **禁止推断因果**：两个指标同期下降，不代表一个导致了另一个。除非有直接等式/机制支撑，否则不写"A 导致 B"、"因为 A 所以 B"。
3. **关联描述用"同期"**：如果想表达两个指标同步变化，只写"A 下降，同期 B 也下降"，不写因果链。
4. **建议和诊断归入"综合诊断"区块**：如果需要给出判断，放在最后的"综合诊断"区块里，并加上"**可能**"、"**需关注**"等限定词，而非断言。

### 示例

❌ 错误写法：
> "Itaquera 折扣菜大量下架（覆盖率 100%→55.56%）→ 首页折扣菜/频道页折扣菜 CTR 清零，折扣活动场景流量彻底断供"

✅ 正确写法：
> "Itaquera 折扣菜覆盖率从 100% 降至 55.56%（-44.44pp）；同期首页折扣菜 CTR 从 3.22% 降至 0%，频道页折扣菜 CTR 从 0.36% 降至 0%。"

> ❌ 历史错误案例（2026-04-23）：Gula Doces 报告中将"折扣菜覆盖率下降"直接写成导致"CTR 清零"的原因，属于无直接证据的因果推断。CTR 下降有多种可能原因（竞争加剧、页面吸引力、平台分配变化等），不能仅凭覆盖率与 CTR 同期下降就断定因果。

**对比周期术语：**
- 单日 → 对比上周同日 → **WoW**（Week-over-Week）
- 周 → 对比上周 → **WoW**
- 月 → 对比上月 → **MoM**（Month-over-Month）
- 自定义多日 → 对比上周同区间 → **PoP**（Point of Period）

**日期解析规则：**
- 单日：`dt = 'YYYYMMDD'`
- 多日/周/月：`dt BETWEEN 'YYYYMMDD' AND 'YYYYMMDD'`，量类指标取 SUM，率类指标取加权 AVG
- ⚠️ **周/月日期边界规则（严格遵守，不得算错）**：

    - 展示给用户的区间必须符合对应 Region 的周边界，不得用错
  - **月**：必须从该月**1号**开始，到该月末（或昨天）结束。例如：4月 = 04-01 ~ 04-30（或 T-1）
  - 展示区间给用户前，必须先验证起始日是否为正确的周起始日（周）或1号（月），验证失败则重新计算
- ⚠️ **天数一致性校验**：当期 X 天 vs 对比期 Y 天，天数不一致时报错：
  > ❌ 当期 X 天 vs 对比期 Y 天，天数不一致，请重新输入对比区间

- 🚨 **日期-星期校验（2026-06-11 强制规则）**：
  > **每次确定日期范围后，必须用 Python 验证日期与星期是否匹配，禁止凭印象判断某天是周几。**

  4. 当期起始 - 7 天 = 对比期起始；对比期起始 + 6 天 = 对比期结束

  6. 验证通过后才能输出给用户或执行查询

### Step 1：获取品牌 id 列表

> ⚠️ **总览查询已经拿到品牌数据，Step 1 直接复用，不重复查询。**

- **方式1（异动品牌）**：从总览结果里筛 `fin_ord_num` WoW 为负的品牌，按跌幅降序取 Top X（过滤 brand_id=0）
- **方式2（大盘监控，仅后线/内部）**：基于总览结果计算波动贡献，取贡献大盘跌幅最大的 Top X（过滤 brand_id=0）。**波动贡献公式（可加型指标专用）**：
  ```
  波动贡献 = (品牌当期订单量 - 品牌对比期订单量) ÷ (大盘当期总订单量 - 大盘对比期总订单量) × 100%
  ```
  含义：该品牌的变化量占大盘整体变化量的比重。分母为大盘净变化量（不含 brand_id=0 的未归属订单），非大盘基期量。

  ⚠️ **根据大盘方向分支处理（必须遵守）**：
  - **大盘下降（grand_curr < grand_prev）**：按贡献值降序取 Top X 负贡献品牌，输出 Top N 并进行深度分析
  - **大盘上升（grand_curr ≥ grand_prev）**：波动贡献排序对下跌品牌的识别价值低（负贡献品牌绝对量都小），不输出波动贡献 Top X。改为：
    1. 统计总览中 WoW 为负的品牌数量
    2. 输出大盘总览 + 负 WoW 品牌数，**询问用户**：
       - 「按跌幅排序看 Top X 异动品牌？」
       - 或「指定品牌 ID 查看？」
    3. 用户选定后再按指定方式输出品牌列表进入 Step 2

  ⚠️ **排序规则（大盘下降时适用）**：对**全量品牌**计算贡献值，按贡献值对大盘跌幅的实际影响排序：
  - 大盘下降（delta_total < 0）时：品牌也下降（delta_brand < 0）→ 贡献值为正，值越大越拖累大盘 → **按贡献值降序**取 Top X
  - 大盘上升（delta_total > 0）时：品牌也上升（delta_brand > 0）→ 贡献值为正，值越大越拉升大盘 → 此为正贡献场景，大盘监控通常关注下跌，视情况处理
  - ⛔ **禁止用 `contribution < 0` 过滤**：大盘下降时正增长品牌贡献值为负（分子正/分母负），过滤后会把正增长品牌排在最前面，结论错误
  - ✅ **正确做法**：不预先过滤正负，直接对全量品牌按贡献值降序排列，取 Top X

  > ⚠️ **大盘定义**：品牌诊断大盘仅包含有品牌归属的订单（brand_id != 0）。brand_id=0 的未归属订单不纳入大盘、不参与贡献排名、不参与任何品牌分析环节。
- **方式3（定向分析）**：跳过，直接使用用户提供的品牌 id 进入 Step 2

> ⚠️ 查询结果中 brand_id = 0 的行为未归属品牌，需过滤跳过，不纳入分析。

**前线 BDM（选项2）的特殊处理：**

总览阶段已完成品牌维度（按波动贡献排序）+ 组织维度（各下属维值升降）的双重输出，**直接询问用户要深入分析的 brand_id**，无需展示分析方式选项。

## 工具调用规则

### 角色 → 工具映射（全程遵守）

| 用户角色 | 数据查询工具 | 适用范围 |
|---------|------------|---------|
| 后线运营 / 其他（选项1/4） | `keeta-data-query` | 总览 + Step 1 + Step 0 + 模块1-5（全数据集查询） |
| 前线 BDM / BD（选项2/3） | `keeta-data-query-for-front-line` | 总览 + Step 1 + Step 0 + 模块1-5（全数据集查询，统一带 --biz-type + --filter） |

### 数据查询的通用规则

- **重要：不要让用户感知到正在跑 SQL，直接呈现查询结果**
- 所有 kdata 命令和 SQL 模板见 `references/sql-templates.md`
- SQL/数据集查询失败时，将完整命令输出给用户，请用户在万象 SQL 探数页面手动执行后粘贴结果
- `kdata --json` 输出时需用 `raw[raw.find('{'):]` 截取 JSON（stderr 有安装日志混入）

### ⚠️ 当期/对比期防写反检查规则（必须严格执行）

**每次向用户输出数据前，必须做以下自检：**

1. **列顺序固定**：任何表格或对比数据，始终按 **「当期 | 对比期 | PoP」** 顺序排列，禁止颠倒
2. **变量名绑定**：代码层始终使用 `curr`（当期）和 `prev`（对比期）命名变量，输出时严格从对应变量取值，禁止手工排列数字
3. **符号一致性检查**：输出前验证 PoP 符号与数值方向一致——
   - 若 curr > prev → PoP 必须为正（+）
   - 若 curr < prev → PoP 必须为负（-）
   - 若符号与方向不符，立即停止输出，重新检查
4. **多指标批量检查**：当同时输出多个指标时，逐条确认每个指标的 curr/prev 取值来自正确的查询结果（当期查询 → curr，对比期查询 → prev），不得混用
5. **子 agent 汇总检查**：多品牌并行分析时，主 agent 汇总前对每个品牌的数据做一遍方向校验，发现异常及时修正后再输出

> ❌ 历史错误案例2（2026-04-23）：并行查询当期/对比期，结果输出顺序不确定，文件写入顺序与预期不一致，导致 curr/prev 又写反。**根治方案：串行查询 + 每次查询前打印日期 label，严禁依赖文件名或输出顺序区分当期/对比期。**

### ⚠️ 营业/体验/流量维度下钻红线（用户纠正，2026-06-11，必须严格执行）

**以下三条为最高优先级红线，违反任一等同于输出不完整报告。**

1. **营业情况 — 在线未营业门店必须列出明细**
   - ⚠️ 每个品牌营业情况层2（在线未营业判断）有结果时，**必须列出所有在线未营业的门店明细**（shop_id、门店名称、is_online_shop、is_open_shop）
   - 查询方式：用供给大盘数据集（60041382）按 `is_online_shop=1 AND is_open_shop=0` 过滤，维度 group-by shop_id,shop_name
   - 🚫 **禁止写"无在线未营业门店"而不查**：必须先执行查询，有数据则列明细，无数据才写"无"
   - 🚫 **禁止只写"有4家在线未营业门店"但不列明细**：必须列出每家门店的信息

2. **体验情况 — 出餐超阈值必须列门店明细**
   - ⚠️ 出餐时长绝对值 > 15min 或 WoW > +10% 即为异常，**有异常门店就必须输出门店级明细表格**（shop_id、门店名称、负责人、出餐时长当期/对比期、WoW）
   - 查询方式：用数据集 62059636，group-by shop_id,shop_name,shop_owner_mis_id，指标 `shop_oavg_readied_duration`，按出餐时长降序
   - 🚫 **禁止只写"出餐16.5min，轻微超过15min阈值"而不列明细**：必须下钻到门店级输出异常门店列表
   - 🚫 **禁止写"共277家门店中有X家超阈值"但不列具体门店**：必须列出超阈值的门店明细

3. **流量渠道 — 曝光UV和CTR下降必须拆解到具体资源位**
   - ⚠️ 当品牌级曝光UV或CTR下降时，**必须拆解到7个具体商家入口资源位**，逐渠道对比当期 vs 对比期，找出下降最多的渠道
   - 7个资源位必须全部出现在汇总表中：品牌墙、Feeds、大搜、高达商卡、折扣菜卡片、金刚区落地页、频道页折扣菜卡片
   - 查询方式：用数据集 62059636，指标 `shop_avg_ad_position_shop_entry_exposure_uv`（总曝光UV）+ 各分渠道曝光UV + `shop_entry_exposure_visit_ratio`（CTR）
   - 🚫 **禁止只写"总曝光UV -10.58%"而不拆解各渠道**：必须输出品牌级7渠道汇总表
   - 🚫 **禁止只写"折扣菜卡片是主要拖累渠道"而不给各渠道具体数值**：每个资源位的当期值、对比期值、PoP 都必须列出

### 多品牌并行分析

- 当需要分析多个品牌时，spawn sub-agents 并行处理
- 每个 sub-agent 负责一个品牌的完整 Step 0 + 5 模块分析
- 主 agent 汇总所有 sub-agent 结果后统一输出
